# Buyer agent MCP

Local stdio MCP server exposing exactly `pay_x402`, `pay_sepa`, `pay_paypal`, `revoke`, and `get_receipt`. Testnet/sandbox only. No owner method, payee change, linking, sweeping, or top-up is exposed.

## Run

Use Node >=22.18 and the root's pinned pnpm version. From the repository root:

```sh
pnpm install --frozen-lockfile
cp agent/mcp/.env.example agent/mcp/.env
pnpm --filter @nearh/agent-mcp start
```

Fill the private file in your editor: the mandate contract ID, the agent's own function-call key on that contract, operator-approved seller origins, and its per-agent M1 service token. `M1_AGENT_TOKEN` must match this agent's entry in the separately running M1 service's `M1_AGENT_TOKENS`. Configure/start M1 using [its README](../../rails/monerium/README.md); its Monerium client ID, secret, and access token belong exclusively to that service. This package never imports the Monerium client or reads owner/rail env files. Its start script reads only `agent/mcp/.env` plus inherited environment, and passes SC1 its settings (`NEAR_AI_*`, `SCAMCHECK_HELD_DIR`); without `NEAR_AI_API_KEY` there it reads the key from `NEAR_AI_ENV_FILE` (default `~/.config/nearh/nearai.env`, skipped if absent) into the scam check only, never into the environment. SC1 itself reads no env file.

Startup requires only the NEAR identity and receipt storage. Seller-origin configuration is checked on x402 calls. M1 configuration is checked before SEPA signing, and the Base Sepolia chain check runs before payment balance reads/signing. Missing payment settings or a Base outage therefore do not prevent NEAR self-revoke or receipt access.

An MCP client can spawn the server directly with `node --env-file-if-exists=.env src/cli.ts`, setting its working directory to `agent/mcp/`. Stdout is MCP only; sanitized startup/decision errors use stderr. No HTTP MCP port is opened. The server uses the maintained [official TypeScript MCP SDK](https://github.com/modelcontextprotocol/typescript-sdk/tree/v1.x) stdio transport.

Run **one process per agent key and receipt directory**, including A1's standalone CLI: A1 coordinates NEAR nonces within one process only. Configure seller origins narrowly; HTTP is accepted only for loopback, HTTPS elsewhere, and redirects are refused. Tool arguments cannot set network endpoints, supply credentials, pick an agent, provide owner assertions, or request raw signing.

## Payment behavior

- `pay_x402({url, method?, body?, reason})` uses A1's scheme and the open `@x402/fetch` client. Just before `signX402`, it sends the actual selected payment requirements to SC1. A1 passes those requirements through `request_signature` and checks the contract-built authorization and signature. A paid result requires a successful Base Sepolia transaction receipt at the seller’s claimed hash, with matching configured-USDC `AuthorizationUsed` (agent and reservation nonce) and `Transfer` (agent, payee and amount) logs; that result is saved before reading the resource body. If the resource body exceeds 64,000 bytes or its stream fails, the result stays `paid`, retains its transaction hash, and reports a resource-delivery error separately; `tx_hash` is the reported Base transaction, while receipts also hold `near_tx_hash`. The settlement header supplies only a claimed hash. Until the chain receipt matches, the result stays `pending` with that hash and is excluded from payment history. `get_receipt` can confirm it later without submitting another payment. While confirmation is pending or the Base RPC is unavailable, the resource body (up to 64,000 bytes) is saved in the private receipt and withheld from tool output until confirmed; a later paid receipt returns it as `response`. The saved HTTP status and any body-read error survive later settlement confirmation, so a paid receipt still explains an HTTP error or missing content. Oversized or interrupted bodies cannot be recovered this way and still report a delivery error; inspect the existing payment before considering any new purchase. No header means an uncertain result, never an invented payment success.
- `pay_sepa({iban, amount, memo, invoice?, reason})` canonicalizes euros, assigns a timestamp and request ID, runs SC1, asks the contract for a payout signature, and calls authenticated `POST /payouts` on local M1 once. M1 reads and verifies the signed reservation itself, checks the current payee allowlist, and owns replay protection and Monerium submission. `submitted` means accepted by M1/Monerium, not bank settlement. The memo is unsigned.
- `pay_paypal({invoice, reason?})` pays a supplier invoice in [supplier/](../../supplier/README.md)'s buyer view (`invoice_id`, `status` `SENT`/`UNPAID`, `amount {currency: USD, value}` canonical as `25.00`, `payee`, `due_date`, `description`). It normalizes the payee as the contract does, runs SC1 on the invoice text with the PayPal rail rules (any result other than `ok` is held or blocked; without a NEAR AI key SC1 skips its rules, so the payment is blocked with `ERR_SCAM_CHECK_UNAVAILABLE`), asks the contract to build and MPC-sign shape 4 (`{type: paypal, payee, amount, timestamp}`; the contract checks the PayPal payee allowlist, cap, budget and window), checks the signed text, and hands `{agent, request_id, payee, amount, timestamp, signature}` once to the local PP3 service ([rails/paypal](../../rails/paypal/README.md)), which verifies the signature and reservation and submits the sandbox payout (`sender_batch_id` derived from agent and `request_id`). The agent never holds PayPal credentials or the PayPal MCP server; it holds only its per-agent PP3 token. Outcomes: `paid` only when PP3 answers `submitted` for this `request_id` with an accepted `payout_batch_id` (not `DENIED`); `held`; `blocked` (contract `ERR_*`, PP3 `PP3_*`, or `DUPLICATE_INVOICE`); `failed` (PayPal or PP3 refused before or without paying); `uncertain` (PP3 pending, a transport failure after signing, or an answer without an accepted batch: inspect PP3's order log; never retried). One open payment per invoice: an invoice with a held, signed, uncertain or paid payment is refused locally; after `failed` or `blocked` it may be paid under a new `request_id`. Payees are masked (`bi…@example.com`) in all output. `paid` means PayPal accepted the batch (`PENDING`), not that the item reached `SUCCESS`. An owner-approved held PayPal payment gets a fresh request ID and timestamp, as SEPA.
- `revoke({})` calls only `revoke_self` with no agent argument. It checks `RevokeResult`, including `revoked` and `key_deleted`; a successful transaction alone is insufficient. The running server retains read-only receipts after revocation. Restarting the signer after its key is deleted requires owner intervention; A1's connect requires a live agent key.
- `get_receipt({request_id})` reads only this agent's request key, refreshes reservation status from NEAR, and retains the rail result/order ID. It never submits a payment. A concurrent lookup merges into the latest receipt so it cannot erase a completed payment’s order ID or transaction metadata. A missing request raises a tool error instead of inventing a status. A signed reservation remains `signed` even when the payout has been submitted; `outcome` records the off-chain result separately. Returned IBANs are masked to their last four characters.

`policy.ts` validates inputs and restricts URLs; it never grants payment authority. An SC1 `ok` or `skipped` still goes through the contract's mandate checks. Contract `ERR_*` codes are returned for blocked payments. A low USDC/EURe float gives `LOW_FLOAT` with an owner notice on stderr as well as in the tool result and does not sign or submit; no agent top-up capability exists. The Base balance check is advisory and can race concurrent spending; the contract remains authoritative for mandate limits. EURe balances use 18 decimals; USDC amounts use base units. SC1 history uses saved completion/request timestamps, never the current lookup time. Seller requirements must identify the requested resource URL before signing. Compare canonical URL forms (including normalized host case/default ports); a different scheme, path or query is still refused.

## `pay_paypal` from scripts (PP5 demo)

```sh
pnpm --filter @nearh/agent-mcp pay-paypal --invoice /abs/path/invoice.json [--reason TEXT]   # or --invoice - for stdin
pnpm --filter @nearh/agent-mcp pay-paypal --receipt <request_id>
pnpm --filter @nearh/agent-mcp pay-paypal --process-decisions   # resume owner-approved holds once
```

Prints the redacted result JSON on stdout; exits 1 only on an error (bad input or config), not on `held`/`blocked`/`failed`/`uncertain`. pnpm runs it in `agent/mcp/`, so pass an absolute invoice path. In code: `import { payPaypalInvoice } from '@nearh/agent-mcp/pay-paypal'` and `await payPaypalInvoice(invoiceJson, { reason })` (builds the buyer from the environment unless `buyer` is passed). It reads `agent/mcp/.env` like `start`, plus `PP3_URL` (default `http://127.0.0.1:8788/payouts`, loopback only) and `PP3_AGENT_TOKEN` (this agent's entry in PP3's `PP3_AGENT_TOKENS`). Run it with the MCP server stopped (one process per agent key and receipt directory). The one-payment-per-invoice guard lives only in the local receipt directory (a payout does not mark the PayPal invoice paid), so the MCP server and the `pay-paypal` CLI must use the same `MCP_RECEIPT_DIR` and contract; with different ones the same invoice can be paid twice. A PP3 duplicate answer (`PAYPAL_DUPLICATE_BATCH`, `PP3_DUPLICATE_REQUEST`) or any answer carrying a `payout_batch_id` is `uncertain` and keeps the invoice blocked from a second payment. Email addresses are masked in PayPal results only; x402 and SEPA outputs are not email-masked.

## Support agent with PayPal refunds (PP-T1)

`src/support.ts` is a merchant-side support agent, separate from the buyer MCP server. A real LLM (NEAR AI Cloud, `SUPPORT_MODEL`, default `deepseek-ai/DeepSeek-V4.1-Flash-1017`) reads a ticket and uses the PayPal Agent Toolkit tools the rail serves (`rails/paypal`, `pnpm refunds`): `get_order` and `get_refund` pass through; `create_refund` runs SC1 on the ticket (`paypal_refund` rail), then `request_signature` with shape 6, then hands the signed order to the rail once. Once a ticket's refund is held, its other refunds are held without asking again. Contract refusals (`ERR_OVER_PER_PAYMENT_CAP`, `ERR_OVER_BUDGET`) go back to the model as `refused`. The process holds its NEAR function-call key, its rail token and the NEAR AI key, never a PayPal credential.

```sh
node --env-file=.env.support src/support-cli.ts --tickets tickets.json [--out transcript.jsonl]
```

Env as `src/support-cli.ts` lists it (`MANDATE_CONTRACT_ID`, `AGENT_NEAR_PRIVATE_KEY`, `PP_REFUND_URL`, `PP3_AGENT_TOKEN`, `NEAR_AI_API_KEY` or `NEAR_AI_ENV_FILE`). Tests: `test/support.test.ts` (scripted model, mocked contract and rail, SC1's real rules). Recorded run: [demo/evidence/pt1-refunds.md](../../demo/evidence/pt1-refunds.md).

## Holds and uncertain outcomes

SC1's `suspicious` and timeout results hold without signing. Without a NEAR AI key, SC1 labels the check `skipped`. The server records the payment and reads the same held queue as DB1 every two seconds. Only a DB1 owner-approved, locally known held request is resumed; x402 keeps its original shape and request ID. Approved SEPA payments preserve the payee and amount but create a fresh timestamp and request ID, as directed by the lead (task 23). The old receipt links to `replacement_request_id`, and the new receipt links back through `approved_from_request_id`; the original is consumed before any signature request and is never replayed. DB1 persists the passkey assertion, and A2 rechecks it against the current contract owner configuration, expiry, signed held ID/status and nonce before signing. The queue ID and payment shape must match the private receipt. Consumed decision nonces prevent replay within this receipt directory. Invalid decisions are blocked individually so later valid decisions can proceed. Rejected requests never sign. The owner proof is verified against the original held ID and saved shape before creating that replacement reservation. This avoids stale payout timestamps without permitting another payee or amount. An interrupted replacement is never automatically retried. An approved x402 request is re-fetched and refused if its selected requirements changed. The agent tools cannot approve a hold.

Receipts default to `agent/mcp/.receipts/<contract>/<agent>/`. Files have mode 600, new directories mode 700; keep them and SC1's held queue private. These records contain payment details, including the private full payout data needed for approval. The MCP output masks IBANs and configured secrets; it does not return the saved operation arguments.

Failures before a signature can be requested return `failed`; once signing/submission starts, interrupted calls are **not automatically retried**, including after a restart. A pending/unknown result is a reason to inspect `get_receipt` and the rail's private order log before requesting anything new. A new tool invocation is a new payment ID; repeating a business invoice with a new ID is not deduplicated. M1 protects one signed request ID, not business invoice identity. A2 must process owner approval while its signed assertion is still valid (at most ten minutes; the owner may choose a shorter expiry). Keep the MCP running while approving. If it starts after expiry, the item becomes blocked with `OWNER_APPROVAL_INVALID`; inspect its receipt and obtain a new owner-approved request rather than editing the queue or replaying the old proof. Expiry is checked against current time, since a writable `decided_at` is not trusted proof of when approval happened. Unsigned legacy queue decisions without the stored proof are blocked; obtain a new owner-approved request. Protect both files and the running code: these checks do not defend against an attacker who controls the local executable or signer keys. There is no new background loop that spends or replenishes a float; polling only handles explicit owner decisions on held requests.

## Verification

```sh
pnpm --filter @nearh/agent-mcp test
pnpm --filter @nearh/agent-mcp lint
```

The focused tests exercise the four-tool surface over the MCP SDK's in-memory transport; A1 and the real open x402 client over a fake NEAR RPC using the mock MPC key; real SC1 timeout/skipped handling; contract-rejection propagation despite scam `ok`; payout signing/handoff, low float, receipts/restart and held approvals; and the authenticated client against M1's real local HTTP server with cryptographic verification and a fake Monerium transport. M1's integration test is JavaScript, matching its runtime-only test boundary; the A2 production TypeScript and TypeScript tests receive strict typechecking. Importing the rail's implementation into A2's strict TypeScript test graph exposed existing `TS2339` errors in `scripts/owner/monerium/src/monerium.ts:113`; this task does not change that owner code.

Initial missing-module RED showed the absent implementation. The subsequent executable test caught the x402 wrapper replacing the original held exception: it returned `failed` instead of `held`. The fix reads the persisted hold state. Tests also distinguish a contract-rejected transaction from a successfully reserved signature. The payment-safety regressions cover a deferred receipt lookup racing payment completion, oversized/interrupted resource bodies after a successful settlement header, and receipt/self-revoke availability with missing or malformed payment configuration and an unavailable Base RPC. The PR-review regressions additionally cover forged settlement headers and mismatched USDC logs, pending confirmation refresh, passkey proof/nonce tampering, per-item queue isolation, fresh reservations for stale approvals, honest history timestamps, low-float notices and pre-sign failures. These are offline integration checks, not new NEAR/Base transactions or bank settlement. No independent or lead-assigned review is claimed.
